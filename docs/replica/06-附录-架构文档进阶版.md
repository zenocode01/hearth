## 1. 项目定位：从 Chatbot 到 Agent 工作台

LobeChat 早期定位是"可一键部署的 ChatGPT 类 Web 应用"（root `package.json`
的 keywords 还保留着 chatbot/chatgpt/nextjs/vercel-ai）。现在的 README.zh-CN
把它重新定义为 **"首席 Agent 运营官"（Your Chief Agent Operator）**：

> 帮你把专属 Agent 组织成 7×24 不打烊的高效队伍：自动招募适配的 AI 队友、
> 调度任务排班、汇总生成工作报告，你始终掌控全局。

核心范式转变：**把 Agent 视为工作单元（Agent as a Unit of Work）**，平台提供
让人与 Agent 共同进化的基础设施。产品叙事分四层（README "特性一览"）：

| 层 | 含义 |
|---|---|
| **运营** | 雇用、排班、汇报：IM 网关（飞书/Slack/Telegram/微信/Line/iMessage/Discord，见 `packages/chat-adapter-*`）把 Agent 接到用户日常 IM |
| **创建** | Agent Builder：描述一次需求即生成可用 Agent 配置；统一接入任意模型/模态；10000+ 技能（builtin tools + MCP） |
| **协作** | Agent Groups / Pages / Schedule / Project / Workspace：多 Agent 并行协作、定时无人值守执行、按项目组织 |
| **进化** | 白盒个人记忆（Personal Memory）：结构化、可编辑、用户完全掌控；Agent 从用户工作方式中持续学习 |

定位里反复出现的态度是"**人始终掌控全局**"（DESIGN.md Voice 一节明确写
"Agents accelerate output, but the user owns the judgment and the final
decision"）——这是它与"全自动 agent 平台"叙事刻意拉开的差异点。

## 2. 总体架构

### 2.1 Monorepo：扁平三层布局

`pnpm-workspace.yaml` + root `package.json` 的 workspaces 字段定义了一个
**扁平（flat）布局**：`apps/`、`packages/`、`src/` 全部位于仓库根目录，
没有嵌套子工作区，无 git submodule（`.agents/skills/project-overview/SKILL.md`
称之为 "Flat layout"）。

```
(repo root, 本身也是一个 workspace: @lobehub/lobehub)
├── apps/
│   ├── web（即根仓库本身）      # Next.js 壳 + Vite SPA
│   ├── desktop/                # Electron 桌面端（独立 npm 包）
│   ├── server/                 # Hono 独立后端服务（router-hono 端点）
│   ├── cli/                    # LobeHub CLI
│   ├── share/、workbench/、auth/ # React Router 独立微前端（Vite 构建，
│   │                           #   产物被根 Next.js copy 进 public/_spa-*）
├── packages/                   # ~80 个 @lobechat/* 内部包
├── src/                        # Web 应用代码（SPA 主体）
├── e2e/                        # Cucumber + Playwright
└── .agents/                    # AI 编码代理的开发规范（见 §4.3）
```

关键机制（root package.json scripts）：

- **构建是多入口 SPA 的拼接**：`build:spa` / `build:spa:auth` /
  `build:spa:workbench` / `build:spa:share` / `build:spa:mobile` 各自是
  `vite build`（不同环境变量：`AUTH=true`、`MOBILE=true` 等），然后
  `build:spa:copy` 用 tsx 脚本把产物复制进 `public/_spa*`，最后 Next.js
  只做 SSR 壳（HTML/auth 壳、tRPC 路由、API）。
- **Dev 体验**：`dev:spa`（纯前端，端口 9876，API 代理到 localhost:3010）+
  线上 **Debug Proxy**（`app.lobehub.com/_dangerous_local_dev_proxy?debug-host=...`
  把线上生产环境加载本地 Vite dev server 的 SPA，支持 HMR + 真实服务器配置）
  —— AGENTS.md 明确说这是开发便利、**不是验收面**。

### 2.2 前端：Next.js 壳内的 Vite SPA

技术栈（`.agents/skills/project-overview/SKILL.md`，版本以 root
package.json 为准）：

| 类别 | 技术 |
|---|---|
| 框架 | Next.js 16（仅做壳：HTML/auth shell、API 路由）+ React 19 |
| 路由 | SPA 内 `react-router`（v8）——`src/spa/entry.{web,mobile,desktop,popup}.tsx` 多入口，`src/spa/router/` 统一注册路由（`desktopRouter.shared.tsx` 注册 Web/Electron 公共路径，`desktopRouter.config*.tsx` 只管平台差异） |
| UI | `@lobehub/ui`（lobe-ui）/ `@lobehub/ui/base-ui`（headless）/ antd 6 |
| 样式 | antd-style（CSS-in-JS，`createStaticStyles` + `cssVar.*` 零运行时优先） |
| 状态 | zustand（`src/store/` 约 35+ 个域 store）+ immer |
| 数据获取 | SWR（`useClientDataSWR` 封装）；服务端通信 tRPC v11 |
| i18n | react-i18next；源码在 `packages/locales/src/default/` |
| 测试 | Vitest（单测/组件）、Cucumber + Playwright（e2e） |

前端目录职责（AGENTS.md "Code Ownership"）：

- `src/routes/` —— 薄页面段，只做组合，不写业务（分 `(main)` `(mobile)`
  `(desktop)` `(popup)` `auth` `onboarding` `share` 组）；
- `src/features/` —— **164 个领域特性目录**（AgentBuilder、AgentGroup*、
  AgentEval*、Document*、Goal*…），业务 UI 与逻辑的归属地；
- `src/store/` —— 域切片 zustand stores；
- `src/services/` —— 客户端 API service（tRPC client 的唯一入口）；
- `src/app/` —— Next.js HTML/auth 壳 + `spa` 模板服务。

**数据流是单向分层**（project-overview skill）：

```
React UI → Store Actions → Client Services → tRPC Lambda
        → Server Services → DB Models (Drizzle) → PostgreSQL
```

- tRPC router 分四类（`apps/server/src/routers/`）：`lambda`（默认）、
  `async`（长任务）、`mobile`（移动端专用）、`tools`（工具）。
- 服务端内再分两层：`services/`（可访问 DB）与 `modules/`（无 DB 访问的
  能力模块：AgentRuntime、ModelRuntime、S3、KeyVaultsEncrypt、
  LLMGenerationTracing…）。tRPC 规范要求**用中间件把 Model 注入 ctx**
  （`authedProcedure.use(serverDatabase).use(...)`），procedure 里不许 new
  Model（`.agents/skills/trpc-router/SKILL.md`）。
- 另有 `apps/server`（Hono）独立进程：webhooks、composio、agent 网关、
  workflows（`router-hono/`）——把不能跑在 Next 运行时里的长任务/回调
  剥出去。
- 客户端数据获取有强纪律（`data-fetching-architecture` skill）：组件不直接
  发请求；service 的 `.query()/.mutate()` → store 的 `useFetchXxx` SWR hook →
  组件读 store；缓存 key 统一由 `src/libs/swr/keys.ts` 域工厂生成，读/刷必须
  构造同一个 key；写后刷新受影响 key；错误用 `AsyncBoundary` 统一渲染
  （区分 undefined / 空数组 / 错误 / 加载中）。

### 2.3 核心领域包（packages/）

| 包 | 职责 | 结构要点 |
|---|---|---|
| `model-runtime` | 模型接入层 | `src/providers/` 下 **50+ provider 适配器**（anthropic、openai、bedrock、google、deepseek、qwen/百炼、lmstudio、comfyui、fal…），统一 core 抽象 |
| `model-bank` | 模型定义与 provider 卡片（元数据、价格、能力） | — |

| `context-engine` | 上下文/提示词管线 | `pipeline/` `processors/` `tokenAccounting/`（token 预算）`providers/` |

| `trpc` | tRPC 客户端/lambda/async 基础设施 | 供 root 与 apps 复用 |
| `agent-signal` / `agent-tracing` / `agent-manager`… | Agent 信号管道、tracing（langfuse）、管理运行时 | — |
| `chat-adapter-*` | IM 网关：feishu/slack/telegram/qq/wechat/line/imessage | 对应"运营"层的 IM 接入 |
| `locales` | i18n 事实源（`src/default/` 英文源 → en-US 手工镜像 → zh-CN 手工翻译 → 其余语言由每日 CI 自动翻译开 PR） | — |
| `env` | 环境 schema（`@/envs/*` → `packages/env/src/*`，t3-oss env-core） | — |
| `business/*`（config/const/model-bank/model-runtime） | **开源 stub**，被云端私有仓库覆盖（见 §4.3） | — |

### 2.4 开源 / 云端双仓库

project-overview skill 明确：本仓库是 **open-source root**，被一个**私有
cloud SaaS 仓库**以 git submodule 形式挂在 `lobehub/` 下消费。cloud 仓库提供：

- `src/business/{client,server}` 与 `packages/business/*` 的真实实现
  （本仓库里是 stub）；
- cloud 专属路由（`(cloud)/`、`embed/`）、store（`subscription/`）、
  tRPC router（billing、budget、risk control）、Vercel cron。
- **文件解析顺序**：cloud 的 `src/store/x` 优先于 `lobehub/packages/store/…`
  再于 `lobehub/src/store/…` —— cloud 覆盖开源默认。

这解释了为什么 `src/business/`、`packages/business/` 里全是薄 stub：
开源版和 SaaS 版共享同一套代码骨架，差异只发生在 business 接缝上。

## 3. 后端与部署形态

- **Web**：Vercel（Next.js + Edge Function + cron）或 Docker 自托管
  （`Dockerfile` + `docker-compose/`，compose 里带 postgresql、redis、
  rustfs(S3)、searxng 检索）；环境变量极简（`OPENAI_API_KEY`、
  `OPENAI_PROXY_URL`、`OPENAI_MODEL_LIST`）。
- **桌面**：Electron（`apps/desktop`，独立 main-process 包
  `apps/desktop/src/main`，`@lobechat/desktop-bridge` /
  `electron-client-ipc` / `electron-server-ipc` 三层 IPC 抽象；
  `local-file-shell`、`device-*` 提供本地设备/沙箱能力；
  Sparkle/OTA 打包流程见 `scripts/electronWorkflow/`）。
- **移动**：React Native **独立仓库**（已发布，不在此 monorepo）；
  本仓库只出 `MOBILE=true` 的 PWA 形态（`index.mobile.html`、
  `mobile-spa` workflow）。
- **CLI**：`apps/cli`（含 `acceptance update` 这类运维命令）。
- **分支策略**：`canary` = 开发/云生产分支，`main` = 发布分支（周期性从
  canary cherry-pick）；新分支从 canary 拉、PR 向 canary 合（AGENTS.md）。

## 4. 设计理念

### 4.1 设计系统（DESIGN.md / DESIGN.dark.md）

- **底座是 lobe-ui（@lobehub/ui）**：LobeHub 自研组件库，语义 token
  （`colorPrimary`/`colorText*/colorBg*/colorFill*/boxShadow*`）经
  ThemeProvider + cssVar（key `lobe-vars`）在运行时可换主题——主色 12 选 1、
  中性色 5 选 1，**组件只许按 token 名消费，不许硬编码 hex**。
- **审美主张是"安静、内容优先"**：默认近中性画布（浅色默认主色就是
  `#222222` 单色，只有用户选主色才带上色相），颜色只承载状态与层级，
  不做装饰；"calm and content-first" 让对话与用户内容保持焦点。
- **层级靠色面与边框，阴影只做点缀**：`boxShadowTertiary` 给抬升卡片、
  `boxShadowSecondary` 给弹层、`boxShadow` 给模态；深色主题里表面
  "越抬越亮"（`#000000 → #0d0d08 → #1a1a1a`）而非靠阴影。
- **4px 间距栅格独立于圆角体系**（4/8/12/16/20/24/32；圆角另走
  4/6/8/12 一档）；一个视图只用一族圆角，禁止混用圆角与直角。
- **组件优先级硬规则**（react skill）：`src/components` →
  `@lobehub/ui/base-ui`（headless 原语，有就必须用它）→ `@lobehub/ui` 根 →
  antd → 自研（最后手段）。**"组合既有规范组件，不要重新发明"**（ux skill：
  sidebar row → `NavItem`，分组 → `Accordion`，不许裸 div 重写 chrome）。
- **移动端/深色不是事后补丁**："every surface ships light + dark,
  desktop + mobile"；`(mobile)` 路由组与 `.mobile`/`.desktop` 组件变体
  是一等公民。
- **Copy 是设计的一部分**（Voice & Content）：术语表固定（Workspace/
  Agent/Group/Context/Memory/Skill/Topic…不许 bot/assistant/agent 漂移）；
  同一动作全局同一动词（Create/Connect/Run/Pause/Retry）；每条消息告诉用户
  下一步做什么；禁止 "Confirm/OK" 裸按钮；**"human warmth" 硬上限**——
  平时 80% 信息 / 20% 温度，关键时刻最多 70/30，最多半句到一句温度，
  必须紧跟明确下一步；避免说教式安慰与过度拟人化。

### 4.2 四条产品价值观（ux skill → design-values.md）

明确标注"Adapted from Ant Design's design values"，LobeHub 全量采纳并
给出**冲突时的优先级**：

1. **自然 Natural**——最小化认知负荷；产品主动推着你走（合理默认、
   AI 辅助决策、平滑过渡），而不是停下来让你琢磨。
2. **意义感 Meaningful**——每个界面锚定用户真实目标，每个动作有即时
   反馈并指向下一个有意义步骤；难度校准，既不过度简化也不砸一堵墙。
3. **确定性 Certainty**——低熵、可预期：同一意图在同一 surface 上行为
   一致（一致性是**语义的**，不是组件的机械一致）；单一焦点；复用同一
   套模式、组件、措辞。
4. **生长性 Growth**——产品随用户一起长：高级能力渐进披露、不挤占新手
   路径；面向人机共生（人机 co-evolution）。

**冲突裁决**：`意义感 ≳ 自然 > 确定性`（不许为"整齐"牺牲用户目标与
前进动量）；生长性是长周期视角，不参与单屏取舍。

每条 checklist 都标注它服务于哪条价值观——**设计原则是带执行检查表
的**：ux skill 按交互类型分 Read（空/加载/错误/失败优先级、1→10k 行
列表、选择态可见、数字 K/M/B 格式化…）、Edit（草稿永不在 reload/失败/
切换时丢失）、Act（一个主按钮、终态屏必须有下一步出口、长任务可取消
可重试、删除必须等服务端成功、secret 只展示一次…）、Feedback（loading
形态有场景表）、Grow（渐进披露、键盘提示必须真的能按）五个 checklist
模块，共 50+ 条可勾选项，每条对应 DESIGN.md 或某条价值观。

### 4.3 工程理念：**为 AI 代理而生的仓库**

这是 LobeHub 工程上最有辨识度的部分——仓库把"AI 编码代理的开发规范"
当成一等公民基础设施：

- **`AGENTS.md`**（repo 根）+ **`.agents/skills/`**（45+ 个 skill：
  react、zustand、trpc-router、drizzle、i18n、deep-review、alint-ruleset、
  acceptance、compose-atoms…）。AGENTS.md 只管仓库级架构与流程，
  **细则全部下沉到 skill，"one source of truth"**（比如 SWR 用法只在
  data-fetching-architecture，组件选择只在 react，Modal 接线只在 modal）。
- **`alint`**（`packages/alint/` + `@alint-js/cli`）：**模型驱动的 lint**
  ——把 eslint 表达不了的"judgement call"规则写进模型可执行的规则集，
  `bun run check --alint` 产生 warning 级发现，"fix 或 justify"。
- **acceptance**（`acceptance` skill + `https://app.lobehub.com/acceptance/<id>`
  报告页）：产品级验收与单元测试/lint/type 是**并列的独立质量门**，
  开 PR 不是重跑验收的触发器——纯重构/文档不跑，新行为必须在真实产品
  上验证并归档证据；PR 描述里贴验收链接。
- **deep-review** skill：普通 review 用 light 模式（一个独立 reviewer 过
  维度清单），显式调用才跑多子代理 deep 模式。
- **其他工程纪律**（AGENTS.md）：
  - 每个 bug fix 必须有"修复前失败、修复后通过"的回归测试；
  - `bun run check [files]` 一把梭（lint + 相关测试 + 类型），**禁止**
    `bun run test` 跑全量；
  - 单文件超过 ~800 行就该拆（"friendly to humans and agents"）；
  - i18n：en-US/zh-CN 必须在同一 PR 手写完成，其余 ~20 种语言靠每日 CI
    （`auto-i18n.yml`）自动翻译开 PR，缺 key 回退英文；
  - commit 前缀 gitmoji；分支 `<type>/<feature>`；lint-staged 覆盖
    ts/tsx/js/md/mdx/json/yml（remark、eslint、stylelint、prettier 全套）；
  - 循环依赖用 `dpdm` 检查（`lint:circular`）作为 CI 门。
- **文档即产品**：`docs/`（changelog / development / self-hosting /
  usage / wiki）由 remark + eslint-mdx 严格 lint，有 `docs:cdn`、
  `docs:seo`（lobe-seo）、`docs:i18n`（lobe-i18n 自动翻译）workflow；
  开发设计文档（agent-goals-design、soft-delete-recycle-bin-design、
  desktop-core-asar-pack-ota-spec…）直接住在 `docs/development/`。

### 4.4 理念 → 机制的对应关系

| 理念 | 落地的机制 |
|---|---|
| 人是最终决策者（控制感） | 白盒可编辑记忆；confirm/进度/可取消长任务；secret 只展示一次；80/20 温度上限 |
| 确定性（低熵交互） | 语义一致性原则；规范组件组合（Nav/Accordion/AsyncBoundary）；token 命名即角色 |
| 自然（低认知负荷） | Debug Proxy（本地前端 × 生产后端）、`bun run check` 单入口、skill 单一事实源、合理默认（单色主色） |
| 生长性（人机共生） | Agent Builder 一次描述生成配置、Agent Groups/Schedule 自动排班、个人记忆持续学习、渐进披露（Grow checklist） |
| 开源可持续运营 | canary/main 双分支、LobeHub Community License（Apache-2.0 + 附加条款）、开源/云双仓库 stub 覆盖、自动 i18n/SEO/changelog/acceptance 流水线 |

## 5. 对做类似产品（如 Hearth）的可借鉴点

1. **分层数据流 + 单向依赖**：`UI → store → service → tRPC → service →
   model → DB`，每层有明确禁令（组件不直接 fetch、procedure 里不 new
   Model、routes 薄化交给 features）。
2. **每个工具/集成一个包**（`builtin-tool-*`）+ 中央注册表，天然可测、
   可裁剪、可单独发版。
3. **设计文档双文件制**：DESIGN.md（token 与视觉/文案系统，YAML frontmatter
   可机读）+ ux skill（交互行为 checklist），静态 vs 动态分离，互不重复。
4. **价值观带优先级**：四条价值观 + 冲突裁决规则，让"设计评审"从审美
   争论变成规则套用。
5. **AGENTS.md + skills 的"单一事实源"组织法**：架构地图放 AGENTS.md，
   细则下沉 skill，规则改动只发生在一处。
6. **quality gate 分层**：lint/类型/单测（CI 硬门）与产品级 acceptance
   （真实环境、报告归档、PR 贴链接）分开，互不替代。
7. **多端 = 多入口 SPA + 壳**：同一个 Vite 工程出 web/mobile/share/
   workbench 多个 SPA，Next 只做壳与 API；Electron 用 bridge/IPC 三件套
   把平台差异收敛到边。
